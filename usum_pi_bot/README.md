# USUM bot with integrated bottom-screen capture

Development version for Raspberry Pi 4 / Linux. The bot owns capture, connection settings and preview. No cc3dsfs or NTRViewer-HR window needs to be opened or arranged.

- **Loopy USB:** direct RGB bottom frames from a modified, pinned cc3dsfs capture helper. No IP is needed for video.
- **NTR wireless:** direct JPEG Compat bottom frames, using the same **3DS IP** as InputRedirection. JPEG quality and bandwidth are adjustable in the bot.
- Detection reads fresh frames independently of the preview. Covering or minimising the bot does not hide its input.
- The latest frame replaces the previous frame; there is no growing video playback queue. Stale or missing feeds are rejected.

Test a single encounter on the capture source you intend to use before enabling automatic repeating. It does not eliminate packet loss or delays generated by the console/network. Wireless timing can still produce suspected-shiny false positives.

## Requirements

- Raspberry Pi 4 or a Linux computer running a Debian-based distribution.
- A graphical desktop, locally or through VNC. Capture does not require visible viewer windows, but the bot has a graphical interface.
- A 3DS with USUM and Luma3DS Rosalina InputRedirection.
- Either a **Loopy New 3DS USB capture board**, or **NTR running on the console** for wireless video.
- Computer and console on the same local network; internet access during installation.

The native USB helper is built on the computer running the bot. This is a Linux development version; the Windows hardware implementation is separate.

## Install

Install Git if it is not already available:

```bash
sudo apt-get update
sudo apt-get install -y git
```

Download the integrated-capture branch and run setup:

```bash
git clone --branch integrated-capture --single-branch \
  https://github.com/AIrahpthos/emu-shiny-hunting-bot.git
cd emu-shiny-hunting-bot/usum_pi_bot
bash Setup_integrated.sh
```

Setup installs dependencies, creates a Python environment, builds the Loopy capture helper and configures USB permissions. The first installation compiles native code and can take several minutes. Reconnect the USB board after setup.

Setup also adds a bot startup entry for **Openbox**. Other desktop environments need their own startup entry pointing to this installation’s Launch.sh. See [desktop startup and headless access](HEADLESS.md).

## Launch

From the installation’s `usum_pi_bot` directory, in a desktop terminal:

```bash
bash Launch.sh
```

No separate capture viewer is needed. For remote operation, first create a desktop session using the [headless guide](HEADLESS.md). An SSH terminal alone does not create that desktop.

## Connect

1. Choose **Loopy USB** or **NTR wireless**.
2. Enter **3DS IP** for the controls. NTR automatically reuses this address for video; Loopy video ignores it.
3. For NTR, set **NTR JPEG quality** and **Bandwidth (Mbps)**. Defaults are 40 and 10 Mbps. The receiver requests bottom-only streaming, with audio and top-screen video disabled.
4. Click **Connect capture**. It starts capture in the background. Connection status appears below the settings.
5. Click **Show bottom screen** to open the live preview in **Screen setup**. Click the preview to select the encounter timing point.

After changing source, IP or NTR settings, click Connect capture again to apply them. **Reconnect capture** forces a fresh connection. Hunt controls lock connection settings while a hunt is active.

**Connect saved capture automatically when the bot opens** is enabled by default on Screen setup. Desktop startup opens the new bot and its saved capture feed. Starting a hunt and confirming its first normal encounter remain manual.

NTR must already be running on the 3DS. This receiver supports **JPEG Compat**, including legacy NTR; Reliable Stream, Delta and lossless modes are not implemented. Nothing needs to be configured in NTRViewer-HR. Close any other viewer using UDP port 8001 first. TCP port 8000 and UDP port 8001 must be reachable on the local network.

## First hunt

Enable Rosalina InputRedirection from the HOME Menu, then launch USUM. Save at a repeatable encounter position. Check the control test, movement duration and bottom-screen detection point.

Leave automatic repeating, failed-attempt retries and capture resumption disabled for the first test. Start the hunt and confirm its first encounter only when the Pokémon is visibly normal and the actual battle menu has appeared.

The loading detector watches blue → black → red. Screen setup provides 10/30/60 Hz checking and a loading timer, defaulting to 16 seconds. Missing the colour sequence leads to an encounter attempt, not proof that loading succeeded.

During encounter triggering, A tapping stops at the detected dark screen. The subsequent first → second screen change is timed with controls released. A suspected shiny or uncertain result stops the bot. Inspect the console yourself; the bot does not catch Pokémon.

Each new run needs a new normal baseline. Keep Ultra Beast mode disabled for ordinary use; it remains only as an optional transition-skipping workaround.

## Recovery and reports

The bot supervises its own feed. The Loopy helper restarts after unexpected exits or five seconds without delivering a complete frame. NTR sends one stream-start request per connection. Initial TCP connection attempts are limited to three; after the request is sent, a control disconnect or video pause does not automatically reconnect or restart the stream. Use **Reconnect capture** if the feed does not return. Actual capture interruptions create incident records and logs visible in **Recovery reports**, which can export a ZIP. NTR video outages count once until fresh frames return; control disconnects and initial connection attempts do not count as outages. Deliberate disconnects when closing or changing capture sources are excluded.

A stalled feed is rejected when no fresh frame arrives within two seconds. The **Resume after capture crash** option can wait for fresh frames and retry an interrupted hunt with its baseline preserved. Automatic retry can discard an unseen shiny. If resumption is off, feed loss stops the hunt while the video receiver continues listening.

Connection chatter, console responses and stream statistics appear on **Capture diagnostics**, not in the hunt console. The diagnostics display retains the latest 500 lines; full NTR logs remain saved for diagnosis. Older NTR reports generated solely by control retries stay saved but are excluded from the interruption count.

The NTR TCP control link and UDP video feed are monitored separately. A control timeout while fresh video is arriving keeps capture running and produces one warning. It does not count as a capture crash or trigger another TCP connection. The UDP receiver remains active so an interrupted stream can return on its own.

A successful control connection does not prove that NTR video is flowing. Detection resumes only after receiving fresh bottom frames. These mechanisms cannot reboot a crashed console or re-enable InputRedirection.

**Retry failed attempts** permits up to three consecutive failed encounter attempts before stopping. A normal result clears the failure streak. No retry overrides an already measured suspected-shiny stop.

Settings live in `settings.json`; logs, screenshots, reset history and incident exports live in `out/`. The native helper is built under `native/` and is not bundled as an ARM binary.

## Update

Stop the hunt and close the bot, then run from the repository directory:

```bash
git pull --ff-only
```

Follow release instructions if an update requires rebuilding the native helper. Launch the bot again afterward. Settings and runtime logs are not tracked by Git and remain in the installation.

## Migrate from an older installation

Install this version in a separate directory. With the old bot closed, copy `settings.json` from the old `usum_pi_bot` directory into the new one to retain connection and hunt preferences. Copy `out/` if you also want the previous logs and encounter history. Gradient reference images are no longer used.

Stop the old capture supervisor and close its viewers before connecting this version. Competing processes can hold the USB device or wireless video port.

Setup backs up the Openbox startup file and replaces entries for recognised legacy installation paths. If the old bot is installed elsewhere, remove its bot/viewer startup entries manually. Other startup commands are preserved. Restart the desktop after stopping the old hunt to apply the new startup configuration.

The backup is saved beside the startup file as `autostart.before-integrated-<timestamp>`. Restore it to return to the former startup configuration. Existing processes are not terminated by setup.

## Validation

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Tests include frame freshness, latest-only delivery, JPEG fragment ordering and loss, bottom-only stream parameters, shared-IP configuration, real local TCP/UDP traffic, and a native-helper pipe simulation. The real USB helper is built separately. Real console video, USB orientation and wireless behaviour still require hardware validation.

## NTR receive-only diagnostic

To compare the integrated detector with an externally started NTR stream, launch
with `SHINY_NTR_RECEIVE_ONLY=1`. The title identifies diagnostic mode. The bot
receives bottom frames on UDP port 8001 and opens no NTR TCP connection. It sends
no heartbeats or stream-start commands. InputRedirection remains active for the
hunt controls.

1. Close the integrated bot so it releases UDP port 8001.
2. Start the stream with the standalone NTR viewer, using its default UDP port
   8001, the same 3DS IP, bottom-screen capture and the desired quality/bandwidth.
3. After the viewer displays the feed, close the viewer to release the port.
4. Start the integrated bot in receive-only mode:

   ```bash
   SHINY_NTR_RECEIVE_ONLY=1 bash Launch.sh
   ```

   From SSH, replace `:1` if your VNC desktop uses a different display:

   ```bash
   nohup env DISPLAY=:1 SHINY_NTR_RECEIVE_ONLY=1 bash Launch.sh > "$HOME/shiny-receive-only.log" 2>&1 < /dev/null &
   ```

5. Select NTR wireless, enter the same 3DS IP and connect capture. Confirm the
   preview receives frames, then start the hunt normally.

Quality and bandwidth settings in the bot do not apply in this mode; the external
viewer establishes them. Reconnect capture restarts the receiver only. If the
console is rebooted, establish the stream again with the standalone viewer before
restarting this test. This mode requires no manual encounter resets. Close the
bot and launch without the environment variable to return to normal NTR control.
